設計原則：引擎是純函式（同樣的名字、日期、次數必得同樣結果），畫面只負責呈現。所以引擎能用單元測試把機率驗到小數點，畫面則靠真實瀏覽器驗。

2. 一局遊戲的狀態（含凶籤出口）

STATE 1
🎴

direct：第一次抽到

吉側：直接存圖分享。凶側：可以「敲木魚重抽」或「認命」。陰筊的隱藏款不能重抽。

STATE 2
🪵

敲木魚（8–32 下，玩家看不到目標）

次數依等級而定，越凶越多。可「我手痠了，幫我敲」自動敲。

STATE 3
🔄

rerolled：重抽結果

吉 → 卡上註記「原抽 X・敲木魚 N 下・改判」，結束。仍凶 → 進入下一步。

STATE 4
🤷

認命 或 化解

認命＝保留手上這支（kept）。化解＝再敲 24–36 下，蓋「已化解」並附一句建議（resolved）。

這四個狀態全部寫成純函式（src/lib/play.ts）並有測試；結果存的是文字快照，所以日後籤池改寫或下架，玩家籤冊裡的卡不會變。

3. 驗證方式（比功能更值得記）

驗證做法抓到什麼
引擎機率單元測試跑 2 萬次，容許 1.5 個百分點—
完整流程真實 Edge、390×844，scripts/e2e-smoke.mjs首頁美術背景一開始沒顯示（CSS 變數放進 background 簡寫無效）
凶籤三條路線用引擎預先算出「會走該路線」的名字，scripts/e2e-bad-paths.mjs測試本身的選擇器寫錯（擲筊按鈕尚未出現就判斷）
籤卡排版挑池裡最長的 38 張 × 2 種結局，量測內文與資訊區的間距日期壓到網址那一行（肉眼看截圖才發現，量測值當時還沒涵蓋）
計數真 Redis 寫入、查詢、清除線上 id 表是舊的，新籤會被擋，所以重新部署後又抽驗 25 筆
線上版對 github.io 再跑一次完整流程—
學到的：「量測通過」和「眼睛看起來對」是兩回事。這次兩個版面問題，都是看截圖才發現的。

4. 美術怎麼接

Claude 無法生圖，所以流程是：docs/ART-PROMPTS.md 寫 prompt → 使用者交給 Codex → 原圖放 art-src/（不進 git）→ scripts/process-art.py 切 sheet、白底墨印轉透明、清殘留點、縮圖轉 webp → public/art/。

  • 25 張 webp 共約 0.9MB。原圖約 20MB，所以不進 repo。
  • 圖載入失敗時畫面仍可用（籤卡退回程式繪製的紙面與手印）。
  • 驗收標準訂了 6 關（一眼認得、一套的、有梗、適合截圖、字要對、情緒對）。
  • 已知不統一：神像、木槌、筊杯是「有外框卡通風」，籤筒、木魚、首頁是「繪本質感」。使用者決定上線後再檢視。

5. 計數的安全設計

風險做法
金鑰外洩Redis token 只存在 Edge Function secrets；提交前掃描 0 命中
別的網站亂打檢查 Origin（實測陌生來源回 403）
偽造資料等級由伺服器用籤 id 反查，不信前端傳的等級；木魚一次最多 40 下
洗數字同 IP 2 秒只收一次（SET NX EX 一個指令）
壞掉任何失敗回 200＋ok:false，前端忽略，遊戲照常

6. 沒做到、還沒驗證的

  • iPhone 的網頁震動：印象中不支援，未驗證；已有畫面震動備援。
  • 存圖到相簿：各機型不同，只測了流程走得到。
  • 籤詩有沒有共鳴：沒有真人驗證。寫手是依檢查器規則調整的，有「為了過關而改」的風險。
  • 每支籤獨立的連結預覽圖、合籤、造籤投稿：V1.1／V2。
