01　舊版診斷與新設計

2026-11-20・M0・目標 11/22 前上線

結論：舊版把力氣花在「介紹網站」和「功能很多」，卻沒有一個讓人想貼出來的瞬間。新版把遊戲縮成一條 15 秒的儀式，結尾是一張寫著你名字的籤。

1. 舊版哪裡不對

我掃過舊版全部 200 支籤與手機畫面，下面都是實際量到的數字，不是印象。

項目量到的結果影響
評語結構200/200 都是「今日宜 X，忌 Y。」抽到第三支就看出同一個模子
內文結構200/200 都剛好兩句，92% 含「你」像編輯寫的短文，不像人說的話
直接引述人說的話0/200沒有「聽得到的那句話」，也就沒有可截圖的句子
即時通訊語境9/200已讀、群組、LINE 這些最有共鳴的場景幾乎沒出現
服務業、輪班1/200整群打工人被排除在外
手機首頁整頁約 2364px，CSS 有 7–12px 的字要捲很久才開始玩，字小到要瞇眼
下載的籤圖沒有名字、沒有日期、大片留白每個人拿到的圖都一樣，沒有理由貼
這些數字只能證明「結構單一、場景有缺口」，不能證明好不好笑。共鳴最後要靠真人判斷，所以上線前會請使用者抽樣標註。

2. 新流程（可以播放）

從進廟到存圖，回訪的人只要約 15 秒。點 ▶ 自動播放，或用左右鍵手動切。

STEP 1
🏮

首頁：一句話、一顆鈕

不放說明卡、不放統計。流程靠引導，不靠文字。

STEP 2
✍️

報上名來

輸入名字。回訪者自動帶入。名字只存在手機裡，不上傳。

STEP 3
😩

最痛的事

六顆選項，可以「換一批」。選了之後，相關的籤被抽到的機率變 4 倍，並印在卡上。

STEP 4
👆

按手印立契約

長按紅印泥約 1 秒，手機震動。手印隨機：指印、掌印、貓掌、狗掌。

STEP 5
🎋

搖籤筒

拖曳搖晃，3 秒內出籤。不用手機感應器，不跳權限視窗。

STEP 6
🌗

擲筊

聖筊 75%、笑筊 22%、陰筊 3%。笑筊後第二擲保證聖筊，不會卡關。

STEP 7
📜

揭曉

蓋印、賜法號、顯示籤卡。吉側直接到存圖；凶側可以敲木魚重抽。

STEP 8
📲

存圖、發 Threads

卡上有你的名字、法號、日期、手印，每個人的圖都不一樣。

3. 凶籤的出口：木魚與化解

抽到不好的籤不是結局，而是一個小遊戲。敲的次數隨機，玩家看不到目標。

flowchart TD
  A[揭曉] --> B{吉還是凶?}
  B -- 吉 --> Z[存圖分享]
  B -- 凶 --> C[敲木魚 8~32 下]
  C --> D[重抽一次]
  D --> E{這次呢?}
  E -- 吉 --> Z2[存圖
註記: 原抽凶 改判]
  E -- 仍凶 --> F{選擇}
  F -- 認命 --> Z3[保留原籤]
  F -- 化解 --> G[再敲 24~36 下]
  G --> Z4[蓋已化解章 附建議]
「放棄」＝認命，保留原籤。「化解」＝再敲一輪並蓋章。這個詮釋已和使用者確認。

500 支夠不夠

用生日悖論近似：同一個朋友圈有 n 個人同時貼出時，至少兩人抽到同一支的機率。

人數200 支500 支
10 人20%9%

500 支夠上線，但只是降低撞籤。卡上還有名字、法號、手印、日期，看起來不會一樣。長期要靠 V2 社群投稿和時令籤輪替。

5. 同名同日同籤

亂數種子 = 名字（去空白、全形轉半形）＋台北日期＋第幾次抽。好處有三個：重新整理不會變；朋友輸入你的名字就能偷看你的籤；不需要後端也能還原結果。代價是換個名字就能重抽，對娛樂產品我認為可以接受。

6. 計數怎麼接（V1 就上）

GitHub Pages 是靜態站，瀏覽器不能放 Redis 金鑰，所以中間要一層代理。

flowchart LR
  B[瀏覽器
GitHub Pages] -- "publishable key" --> F[Supabase Edge Function
count]
  F -- "Redis token (secret)" --> R[(Upstash Redis
otld: 前綴)]
  F -. "來源檢查 + 限流 + 驗證籤 id" .-> F
防護做法
金鑰不外洩Redis token 只存在 Edge Function 的 secrets，前端只有 publishable key
擋陌生網站檢查 Origin，只放行自己的網站與本機
不信前端傳的值日期由伺服器算；等級由「籤 id」反查，不用前端傳的等級
防洗數字同一個 IP 2 秒內只收一次；木魚一次最多 40 下
壞掉不影響遊戲任何失敗都回 200，前端直接忽略，只是不顯示數字
新式 publishable key 不會被 Supabase 平台驗證，所以這個函式設 verify_jwt=false，由函式自己比對 apikey 標頭。實測：錯的 key、沒有 key、陌生來源都被擋；用對的 key 但 Redis 還沒設定時回 not-configured。

7. 取捨

沒選的方案為什麼
V1 就做造籤與共用籤筒門檻高、要審核，而且不是讓人想貼的那個瞬間。改到 V2，只收一句話。
用 Supabase 資料表計數也做得到，但使用者明確要 Redis。
用手機感應器搖籤iOS 要跳權限視窗，會打斷流程。改用拖曳。
每支籤獨立的預覽圖靜態站要在建置時預先產生，工作量大，放 V1.1。

8. 還沒驗證的事

  • iPhone 能不能震動：我印象中 iOS Safari 不支援，但沒確認，所以畫面震動是必備備援。
  • 存圖到相簿：各手機的行為不同，要用實機測。
  • 籤詩有不有共鳴：要請使用者抽樣標註。
  • Edge Function 在 Redis 設定好之後的完整流程：待使用者設定 secrets。
